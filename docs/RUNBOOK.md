# تشغيل وصيانة مدار

## إعداد البيئة

ابدأ بأوامر README. ملف `.env.example` قالب فقط؛ وينشئ `pnpm env:init` ملفًا محليًا بمفتاح عشوائي. لا تنسخ كلمة مرور PostgreSQL المحلية إلى الإنتاج. تقرأ التطبيقات البيئة عند بدء التشغيل، ويتطلب تعديلها إعادة التشغيل.

| المتغير                    | الافتراضي أو المعنى                                                   |
| -------------------------- | -------------------------------------------------------------------- |
| `DATABASE_URL`             | إلزامي للخدمات؛ استخدم حسابًا منفصلًا لكل بيئة                          |
| `NODE_ENV`                 | `development`؛ يحجب الإنتاج البيانات التجريبية ويمنع جمعها وبذرها     |
| `HOST`                     | `127.0.0.1` في التطوير؛ و`0.0.0.0` داخل الحاوية فقط                  |
| `API_PORT` / `WEB_PORT`    | `4100` / `3100` عند تشغيل `pnpm dev`                                 |
| `API_INTERNAL_URL`         | عنوان API الذي يستخدمه خادم الويب؛ لا تستخدم `NEXT_PUBLIC`            |
| `ADMIN_API_KEY`            | 32 حرفًا فأكثر؛ إلزامي في API الإنتاج، وغيابه محليًا يعطل إدارة المصادر |
| `ENABLE_NETWORK_INGESTION` | `false`؛ لا يعمل RSS الخارجي حتى تغييره صراحةً                         |
| `WORKER_POLL_SECONDS`      | `30`؛ فترة بحث العامل عن المصادر المستحقة، وليست فاصل كل مصدر        |
| `LOG_LEVEL`                | مستوى سجل العامل؛ يستخدم API سجل طلبات Fastify                       |

لا توجد مفاتيح OpenAI أو X أو مزود إشعارات في هذه المرحلة.

## فحوص التشغيل

```sh
curl --fail http://127.0.0.1:4100/health/live
curl --fail http://127.0.0.1:4100/health/ready
curl --fail http://127.0.0.1:4100/v1/articles
```

يؤكد `live` استجابة API. ويتحقق `ready` من اتصال قاعدة البيانات والترحيلات المطلوبة، لا من توفر جميع المصادر أو سلامة العامل. راقب أيضًا سجل `Madar worker started` وجداول `fetch_runs` و`last_success_at` والطوابير.

```sql
SELECT name, enabled, rights_status, last_success_at, next_fetch_at, last_error_code
FROM sources ORDER BY next_fetch_at;
SELECT source_id, status, finished_at, discovered, inserted, updated, error_code
FROM fetch_runs ORDER BY finished_at DESC LIMIT 30;
SELECT name, state, count(*) FROM pgboss.job GROUP BY name, state;
```

لا تطبع `feed_url` في مراقبة عامة؛ فقد يحتوي رمز وصول. يُدار عنوان المصدر داخليًا ولا يظهر في DTO العام.

## الترحيلات والتراجع

ينفذ `pnpm db:migrate` ملفات SQL بالترتيب، بقفل استشاري ومعاملة لكل ترحيل، وبصمة تمنع تغيير ترحيل سبق تطبيقه. لا يعدّل `db:seed` مصدرًا قائمًا ولا يعمل في الإنتاج. يهيئ pg-boss مخططه عند بدء API أو العامل؛ وتتطلب بيئة الإنتاج فصل صلاحيات الترحيل والتحقق من توافق إصدار المكتبة مع مخططها قبل ترقية الخدمات.

لا يُعكس الترحيل الخاطئ تلقائيًا. أوقف الكتابة، واختبر ترحيلًا تصحيحيًا على نسخة معزولة، ثم طبقه أو استعد نسخة احتياطية وفق أثره. لا تستخدم `docker compose down -v` كإجراء تشغيل اعتيادي؛ فهو يحذف بيانات قاعدة الحاوية.

## الفشل والطابور

توجد ثلاث محاولات إضافية للمهمة الفاشلة، بتأخير يبدأ من 30 ثانية ويتراجع أسيًا حتى سقف 300 ثانية. تنتهي المهمة بعد 120 ثانية، والحد الأقصى لجلب التغذية 8 ثوانٍ. يحتفظ الطابور بالمهمة المكتملة يومًا وبالفاشلة 7 أيام. قد تؤدي مواصلة مصدر معطل إلى مهمة جديدة عند موعده التالي؛ راقبه ثم أوقفه بدل تركه يعيد المحاولة إلى ما لا نهاية.

عند تعطل مصدر، افحص `last_error_code`، وتحقق يدويًا من العنوان والحقوق، وأوقف المصدر عبر PATCH إذا لزم. لا تتجاوز فحص DNS أو قواعد HTTPS لمعالجة الفشل. تُرفض تحويلات HTTP 3xx؛ غيّر عنوان التغذية إلى الوجهة المعتمدة بعد فحصها.

لإعادة مهمة بعد إصلاح السبب، استخدم `/v1/admin/sources/{id}/collect`؛ إذ يمنع النظام تكرار التخزين. لا تحذف صفوف pg-boss يدويًا أثناء العمل. يدعم التطوير إيقافًا متدرجًا بإشارة SIGTERM.

## النسخ الاحتياطي

قبل الإطلاق، فعّل نسخ PostgreSQL المجدولة والتشفير وPITR لدى المزود؛ فلا توجد خدمة نسخ سحابية مهيأة الآن. يجب أن تشمل نسخة `pg_dump -Fc` مخططي التطبيق وpgboss. لا تحتوي القاعدة النصوص الخام الكاملة أو الصور.

للتطوير، استخدم `pg_dump` مع بيانات الاتصال من `.env` عبر متغيرات PostgreSQL القياسية، واحفظ الناتج في `.local/backups/` المستثنى من Git. لا تكتب رابطًا يحوي كلمة مرور في وثائق عامة أو سجل. اختبر `pg_restore` إلى **قاعدة جديدة معزولة**، ثم تحقق من أعداد المصادر والمواد والنسخ ومن `/health/ready` بعد تطبيق الترحيلات.

إنشاء ملف وحده لا يثبت نجاح النسخ الاحتياطي؛ فدليل الاستعادة شرط قبول الإنتاج. لم يُتفق بعد على أهداف زمن الاستعادة وفقد البيانات، ولا ندعي تحقيقها في هذه المرحلة.

## تشغيل الحاويات

```sh
pnpm env:init
docker compose --profile app up --build
```

هذه بيئة محلية: المنافذ مكشوفة على loopback فقط، وبيانات PostgreSQL في volume، ويحدد ملف `.env` المحلي بيئة التطوير. يسبق الترحيل بدء الخدمات. تعمل الحاوية النهائية بمستخدم `node`، ويستخدم الويب ناتج Next standalone مع الملفات الثابتة و`public`.

يتطلب الإنتاج قاعدة وأسرارًا منفصلة، و`NODE_ENV=production`، وTLS وreverse proxy، وشبكة خاصة لـPostgreSQL وAPI الإداري، وصلاحيات أقل، ومخارج شبكة محكومة، ومراقبة ونسخًا احتياطيًا، ومراجعة الحقوق والاحتفاظ. يشمل Dockerfile أدوات البناء في أول تسليم؛ وتحسين حجمه وفصل حساب الترحيلات عمل مطلوب قبل الإطلاق.

## CI

ينفذ GitHub Actions التثبيت المقفل وlint وفحص الأنواع واختبارات الوحدات والبناء وتكامل PostgreSQL وفحص تبعيات الإنتاج، مع مهمة لبناء الحاوية. توثق `ACCEPTANCE.md` حالة التنفيذ الفعلية؛ فوجود ملف YAML وحده لا يثبت نجاحه على GitHub.
